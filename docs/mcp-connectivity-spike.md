# Playwright MCP Connectivity Spike Runbook

## Purpose and strict scope

This spike tested one narrow path: a Python process started the repository's
locally installed Playwright MCP Node CLI as a child process, initialized an MCP
client session over stdio, discovered tools dynamically, navigated Chromium to
`https://example.com`, took a snapshot, and shut down cleanly.

It is a connectivity experiment, not a general MCP gateway, policy engine, or
browser agent.

## Verified environment

- Verification date: `2026-07-27`
- Node.js: `v20.19.0`
- npm: `10.8.2`
- Python: `3.12.13`
- Python MCP SDK: `mcp 1.28.1`
- Playwright MCP: `@playwright/mcp 0.0.78`
- Playwright dependency used by Playwright MCP:
  `1.62.0-alpha-1783623505000`

## Architecture and data flow

```text
Python spike
  -> starts local Node CLI from node_modules
  -> exchanges MCP messages over child-process stdin/stdout
  -> initializes ClientSession
  -> list_tools
  -> writes the real tool inventory
  -> browser_navigate(https://example.com)
  -> browser_snapshot
  -> browser_close, when available
  -> closes the MCP session and child process
```

No MCP network port, HTTP transport, or SSE transport is used.

The documented installation commands are:

```bash
python -m pip install -r requirements.txt
npm install
```

The verified environment successfully installed Chromium with:

```bash
./node_modules/.bin/playwright install --with-deps chromium
```

Using the repository-local CLI ensures the browser installation matches the
Playwright version resolved in `package-lock.json`.

Browser installation remains environment-dependent. A possible generic command
for a future environment is:

```bash
npx playwright install chromium
```

## Verified live connectivity result

Command:

```bash
python scripts/mcp_connectivity_spike.py
```

Result:

- stdout: `Playwright MCP connectivity spike succeeded`
- stderr: empty
- process exit code: `0`

The run verified that the local Node child process started; Playwright MCP
communicated through stdio; MCP initialization and `list_tools` completed; 24
tools were discovered; and the real inventory was written. It also verified
that `browser_navigate` successfully navigated to `https://example.com`,
`browser_snapshot` returned usable content, and `browser_close` completed
without producing an error. The MCP session and child process exited
successfully, and no MCP network port was exposed.

Exit code 0 proves that this specific configured local stdio flow completed its
implemented checks successfully in the verified environment. It does not prove
that arbitrary sites or tools are safe, that every advertised tool works, or
that authorization and policy enforcement exist.

## Verified controlled blocked-origin failure

For this controlled probe, a temporary copy of the script changed the target
URL from `https://example.com` to `https://not-allowed.invalid`. The committed
script and real MCP configuration were not modified. The temporary copy was
deleted after the probe and was never committed.

Result:

- stdout: empty
- stderr included:
  - `Playwright MCP connectivity spike failed`
  - `startup, invocation, or shutdown error`
  - `invocation error: browser_navigate returned an MCP error`
  - `net::ERR_BLOCKED_BY_CLIENT`
- process exit code: `1`

This verified that the configured allowed-origin restriction blocked this
navigation, useful nested error details were visible in normal CLI output, and
the failure returned a non-zero exit code. It demonstrates one configured
guardrail on this controlled path; it does not establish the origin allowlist
as a complete security boundary.

## Discovered capability versus permission

The 24-tool inventory includes:

- `browser_navigate`
- `browser_snapshot`
- `browser_close`
- `browser_evaluate`
- `browser_file_upload`
- `browser_run_code_unsafe`

The inventory records capabilities advertised by the server, not capabilities
authorized for use. Only `browser_navigate`, `browser_snapshot`, and
`browser_close` were invoked. `browser_evaluate`, `browser_file_upload`, and
`browser_run_code_unsafe` were not called. No upload or download operation was
performed. Tool authorization, classification, filtering, and policy
enforcement remain work for a later milestone.

## Success criteria

The verified run demonstrated all technical connectivity criteria:

1. The local Node CLI starts as a child process over stdio.
2. The Python SDK initializes the MCP session.
3. `list_tools` returns a real tool catalog.
4. `browser_navigate` and `browser_snapshot` are present.
5. The real, deterministic inventory is written.
6. Navigation to `https://example.com` and a snapshot return usable content.
7. `browser_close` is called when exposed, and resources shut down cleanly.
8. The script exited with code zero.

## Failure categories and cleanup

The script distinguishes repository/configuration startup problems, missing
Node or Python dependencies, a missing local CLI, MCP initialization failures,
missing required tools, invocation failures, timeouts, and shutdown failures.
When `browser_close` is advertised, the script always attempts it, including
after a navigate or snapshot failure. A primary operation failure is preserved;
a shutdown failure is reported when it is the only failure; and both the
primary failure and additional shutdown failure are reported when both occur.
The handling does not broadly catch `KeyboardInterrupt`, `SystemExit`,
cancellation, or other conditions derived only from `BaseException`.

For nested `ExceptionGroup` instances, the script recursively extracts
distinct, non-empty leaf exception messages in deterministic first-seen order.
This prevents a generic TaskGroup summary from hiding useful nested details and
removes duplicate leaf messages. The SDK context managers own session and
child-process cleanup, including when an operation fails. The isolated browser
profile is not persisted.

## Security boundaries and exclusions

The configuration enables Chromium, headless and isolated operation, core
capabilities only, omitted image responses, disabled code generation, and
restricted file access. The browser allowlist contains only
`https://example.com`. The upstream origin allowlist is a spike guardrail, not
a complete security boundary and may not constrain redirects; the client also
hard-codes the single public target URL.

The allowed-origin configuration is a defensive measure, not a complete
security boundary. Local MCP transport also does not make content returned by a
target website trusted.

The run did not exercise `browser_evaluate`, `browser_run_code_unsafe`, file
uploads, downloads, credentials, initialization scripts, persistent
authenticated state, unsafe code execution, LLMs, agent loops, FastAPI or other
APIs, persistence, vLLM, Docker, devtools, PDF, or vision capabilities. Unsafe
and deferred tools being present in discovery does not authorize them.
